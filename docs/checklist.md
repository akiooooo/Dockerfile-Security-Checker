# Стандарт Dockerfile: требования и чек-лист

Версия стандарта: **1.0**, дата проверки источников: **10.11.2026**. Область: Linux-образы приложений и CLI. Это локальная учебная политика, а не полный CIS Benchmark. Уровни ниже выбраны для этого проекта; официальная документация Docker не назначает им наши коды DFxxx.

## Автоматические проверки

| ID / уровень | Что проверить | Почему и как исправить | Исключение / предел проверки | Основание |
| --- | --- | --- | --- | --- |
| DF001 / warning | У внешнего `FROM` есть тег либо digest | Неявный тег обычно означает latest; укажите выбранную версию | `scratch` и ссылки на предыдущую стадию исключены; порт registry не считается тегом | S1, S2 |
| DF002 / warning | Не используется `:latest` без digest | Плавающий тег осложняет воспроизведение сборки | `latest@sha256:...` уже закреплён по содержимому | S1 |
| DF003 / info | Базовый образ закреплён digest | Digest фиксирует содержимое; настройте управляемое обновление | Закреплённый digest сам по себе не гарантирует отсутствие CVE; правило необязательное | S1 |
| DF004 / warning | Значение переменной в `FROM` известно | Без значения невозможно проверить версию образа | Учитываются простые глобальные ARG со значением по умолчанию; build-arg из CI неизвестен | S2 |
| DF005 / warning | Для финальной стадии указан `USER` | Явно документирует ограничение привилегий | Внешний базовый образ уже может иметь безопасного пользователя; registry не опрашивается | S1, S2 |
| DF006 / error | Последний действующий `USER` не root/0 | Ограничивает последствия компрометации приложения | Root в builder допустим; rootless daemon и USER образа - разные уровни защиты | S2, S6 |
| DF007 / error | Секретные параметры не передаются через ARG/ENV | Такие значения могут попасть в метаданные/образ; используйте secret mount | Поиск по имени переменной, не доказательство наличия секрета; публичные токены могут требовать исключения | S3, S4 |
| DF008 / error | COPY/ADD явно не переносит `.env`, `.git`, `.ssh`, приватные ключи известных имён | Не сохраняйте секреты и служебные данные в слое | `.env.example`/`.env.sample` разрешены; полный поиск секретов в контексте не выполняется | S4, S5 |
| DF009 / warning | Удалённый ADD проверяется по checksum | Исключает неконтролируемую подмену скачанного содержимого | Локальное распаковывание ADD допустимо; наличие checksum проверяется синтаксически, не криптографически | S2 |
| DF010 / error | Нет прямого `curl/wget ... \| sh/bash` | Удалённый ответ сразу становится кодом; отделите загрузку и проверку | Не выполняется анализ содержимого скрипта или всех shell-обёрток | S4; политика проекта |
| DF011 / error | TLS-проверка curl/wget не отключена | Без проверки сертификата проще подменить загрузку | Собственный CA следует подключить, а не заменять флагом insecure | S7, S8 |
| DF012 / warning | apt-get update и install в одном RUN | Кеш отдельных слоёв может сохранить устаревший индекс | Признанный cache mount для apt рассматривается отдельно; ветвления shell не доказываются | S1 |
| DF013 / warning | apt-get install использует `--no-install-recommends` | Снижает набор необязательных пакетов | Если рекомендуемые пакеты нужны приложению - обоснуйте исключение | S1 |
| DF014 / warning | Списки apt очищены в том же RUN | Удаление в следующем слое не уменьшает предыдущий | `apt-get clean` не равен удалению `/var/lib/apt/lists/*`; поддержан cache mount | S1, S9 |
| DF015 / warning | apk не оставляет индекс кеша | Используйте `--no-cache` либо удаляйте `/var/cache/apk` в том же RUN | Это проверка распространённого паттерна, не измерение размера слоя | S10 |
| DF016 / info | pip не сохраняет лишний кеш в слое | Используйте `--no-cache-dir` или отдельный cache mount | Учитываются PIP_NO_CACHE_DIR из ENV до команды и cache mount с `.cache/pip` | S9, S11 |
| DF017 / warning | В финальной стадии предпочитается npm ci | Lockfile обеспечивает проверяемую установку зависимостей | `npm install -g` исключён; npm install в builder не считается нарушением этого правила | S12; политика проекта |
| DF018 / warning | CMD и ENTRYPOINT в exec-форме | Облегчает доставку сигналов основному процессу | Shell-форма иногда нужна; JSON `sh -c` также требует проверки разработчиком | S2, S13 |
| DF019 / warning | WORKDIR абсолютный | Не зависит от каталога, заданного базовым образом | Переменные не раскрываются полностью; Windows drive path не отмечается этим правилом | S14 |
| DF020 / error | Нет распространённого `chmod 777` | Не выдавайте запись всем пользователям; настройте владельца и минимальные права | Права внутри скриптов, числовых переменных и symbolic modes полностью не анализируются | Политика проекта |
| DF021 / warning | Не используется sudo в RUN | Усложняет модель пользователя и передачу сигналов | Это рекомендация для обычных Docker-сборок, не запрет всех способов смены пользователя | S1 |
| DF022 / info | Есть HEALTHCHECK или описана внешняя проверка | Помогает отличить запущенный процесс от исправного сервиса | CLI, библиотеки и сервисы с probes оркестратора могут не иметь HEALTHCHECK | S2 |
| DF023 / warning | При COPY . есть непустой .dockerignore | Уменьшает контекст и вероятность копирования лишнего | Проверка не доказывает полноту шаблонов; `COPY --from` исключён | S5 |
| DF024 / info | Вместо MAINTAINER используется LABEL | Современный механизм метаданных | Не относится непосредственно к уязвимости образа | S2, S15 |
| DF025 / info | Ключевые слова в верхнем регистре | Упрощает чтение и обзор изменений | Семантика Docker от регистра не зависит; единственное правило с автоисправлением | S2; стиль проекта |
| DF026 / warning | ONBUILD осознан и документирован | Триггер исполнится в чужой downstream-сборке | Полезен для специальных базовых образов; автоматического запрета нет | S2 |

`PARSE` - техническая ошибка разбора, а не 27-е правило политики. После неё анализ конкретного файла прекращается.

## Чек-лист ручного ревью

Эти пункты важны, но статический скрипт **не выдаёт их за автоматически проверенные**:

- [ ] Образ получен от доверенного поставщика; проверены происхождение, подпись и процесс обновления.
- [ ] Размер и состав runtime-образа обоснованы; компиляторы и тестовые инструменты по возможности оставлены в builder.
- [ ] Финальная стадия multi-stage действительно копирует только необходимые артефакты.
- [ ] Образ просканирован на CVE; проверены достижимость проблем и доступные обновления.
- [ ] Секреты исключены из контекста, слоёв, логов и build arguments; при утечке они отозваны, а не просто удалены в новом слое.
- [ ] Настроены SBOM и происхождение сборки, когда это требуется процессом поставки.
- [ ] Зависимости приложения закреплены lockfile; обновления и исключения контролируются.
- [ ] Приложение работает под непривилегированным UID; нужные каталоги доступны ему без chmod 777.
- [ ] Проверены остановка по SIGTERM, обработка дочерних процессов и необходимость init-процесса.
- [ ] Для сервиса есть проверка здоровья и готовности; для CLI её отсутствие обосновано.
- [ ] В runtime не используются `--privileged`, host namespaces и лишние capabilities без необходимости.
- [ ] Установлены лимиты CPU/памяти, ограничения PID, seccomp/AppArmor и read-only root filesystem, где это возможно.
- [ ] Docker socket не передаётся приложению без отдельной модели угроз.
- [ ] Контейнер не считается полноценной границей для враждебного кода только потому, что у него есть namespaces.
- [ ] Сборка и тестовый запуск выполняются в CI; исключения имеют владельца и срок пересмотра.

## Как применять стандарт

Начальный порог - `warning`: новые ошибки и предупреждения блокируют изменение. Для постепенного внедрения в старом проекте можно начать с `error`, зарегистрировать исключения и поэтапно повышать требования. Нельзя понижать серьёзность всех результатов только ради зелёной сборки.

Каждое исключение должно объяснять конкретный случай. Для большого проекта стоит дополнительно вести владельца и дату пересмотра исключений во внешнем процессе ревью; текущий инструмент хранит только причину в комментарии и счётчик подавлений.
