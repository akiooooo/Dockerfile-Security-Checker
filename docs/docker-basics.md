# Кратко о Docker и границах проверки

## Образ, контейнер и слои

Dockerfile описывает сборку образа. Образ — набор слоёв файловой системы и метаданных запуска; контейнер — запущенный процесс или группа процессов на его основе. Контейнер не содержит отдельное ядро ОС, как обычная виртуальная машина.

Инструкции, меняющие файловую систему, формируют слои. Если секрет сначала скопирован, а затем удалён отдельным RUN, он может остаться в предыдущем слое. По той же причине очистка кеша в следующем RUN не убирает его из уже созданного слоя. При этом не каждая инструкция Dockerfile обязательно добавляет слой с файлами: USER, CMD и другие настройки меняют конфигурацию образа.

## Namespaces и cgroups

Linux namespaces дают процессам отдельное представление PID, сети, mount points и других ресурсов. Cgroups учитывают и ограничивают использование ресурсов. Дополнительные механизмы — capabilities, seccomp, AppArmor/SELinux и режим rootless. Это взаимодополняющие уровни, а не абсолютная гарантия изоляции.

Dockerfile может задать пользователя и некоторые метаданные, но не доказывает, что контейнер запустят без `--privileged`, с лимитами памяти или без доступа к Docker socket. Для этого нужен анализ runtime-конфигурации и хоста. Основание: [Docker Engine security](https://docs.docker.com/engine/security/).

## CMD и ENTRYPOINT

`ENTRYPOINT` обычно задаёт основной исполняемый файл, `CMD` — команду по умолчанию либо аргументы к нему. Пользователь может переопределить их при запуске. Exec-форма — JSON-массив строк; shell-форма передаёт строку оболочке.

```dockerfile
ENTRYPOINT ["python", "-m", "http.server"]
CMD ["8080"]
```

В таком примере `docker run image 9000` заменяет аргумент по умолчанию. Shell-форма добавляет оболочку между runtime и приложением; корректность доставки сигналов зависит от её поведения и использования exec. Даже JSON `["sh", "-c", "..."]` не избавляет от необходимости продумать сигналы. Основание: [Dockerfile reference](https://docs.docker.com/reference/dockerfile/#understand-how-cmd-and-entrypoint-interact).

## Multi-stage build

Стадия сборки может содержать компилятор и работать под root. Финальная стадия получает только исполняемый файл или нужные зависимости через `COPY --from=...`. Это уменьшает состав runtime-образа. Но любой multi-stage Dockerfile всё равно требует ревью: можно случайно скопировать лишние файлы или оставить root в runtime.

Анализатор отслеживает стадии текущего файла, учитывает наследование USER и HEALTHCHECK через `FROM previous-stage` и применяет runtime-проверки к последней стадии либо `--target`. Образы из registry не загружаются. Основание: [Docker multi-stage builds](https://docs.docker.com/build/building/multi-stage/).
