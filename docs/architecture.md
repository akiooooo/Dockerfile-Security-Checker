# Алгоритм и устройство приложения

## Этапы обработки

1. CLI проверяет аргументы и находит входные файлы. Совпадающие пути не проверяются повторно.
2. Исходник читается как UTF-8/UTF-8 BOM, сохраняются исходные номера строк.
3. Парсер объединяет переносы, отделяет инструкции, обрабатывает JSON и простые heredoc, строит стадии.
4. При ошибке синтаксиса создаётся PARSE и проверка этого файла останавливается. Проверка следующих файлов продолжается.
5. Определяются ссылки на предыдущие стадии и действующие USER/HEALTHCHECK. Последняя стадия или --target считается runtime-целью.
6. Проверки запускаются на уровнях внешнего FROM, каждой инструкции и runtime-цели. Глобальные ARG также проверяются.
7. Проверяются исключения. Неизвестные ID - ошибка настройки; подавленные находки считаются отдельно.
8. Результаты сортируются по строке и ID, преобразуются в текст, JSON или SARIF.
9. CLI выбирает код завершения по порогу. PARSE всегда даёт неуспех проверки.

Схема: [SVG](algorithm.svg), [Mermaid](algorithm.mmd).

## Модели и ответственность

`Instruction` хранит ключевое слово, значение, исходный регистр, диапазон строк и исключения. `Stage` содержит базовый образ, alias, родительскую стадию и собственные инструкции. `Document` объединяет исходник и стадии. `Finding` не хранит аргументы Dockerfile, чтобы не копировать возможные секреты в отчёт. `Report` - результат одного файла.

`Rule` задаёт ID, уровень, заголовок, рекомендацию и область применения. Само условие проверки находится в одной из трёх функций правил. Это компромисс учебного проекта: модель расширяется простым добавлением условия и тестов, без загрузки плагинов или исполнения внешней конфигурации.

## Shell-анализ

`shlex` отделяет типовые команды и разделители; текст внутри кавычек не становится отдельной командой. Проверяется, какая программа вызывается, а не только наличие слова curl или chmod в строке. Поддерживается вложенный `sh -c` ограниченной глубины. Прямой pipeline загрузчика в shell проверяется с учётом разделителя `|`.

Это не Bash AST и не символьное исполнение. Условные ветви, функции, command substitutions, wrappers и сложные подстановки могут скрыть риск или породить неточную рекомендацию. Скрипт не исполняет найденный shell-код.

## Автоисправление отдельно от правил

Разбор определяет физическую строку ключевого слова. Исправление меняет только её начальное слово. Heredoc и продолжения остаются побайтово неизменными. До записи сверяется исходник, затем создаётся эксклюзивная .bak, временный файл записывается и заменяет оригинал. Уже существующая .bak блокирует запись. Визуальный diff показывает только ключевые слова и скрывает аргументы.

При нескольких входных файлах изменения выполняются пофайлово, а не общей транзакцией. Если следующий файл вызовет ошибку, предыдущие уже могут быть исправлены; резервная копия сохраняется для каждого изменённого файла. Откат: после просмотра заменить файл содержимым его `.bak`.

## Ограничения сложности

Парсинг проходит по физическим строкам. Проверки выполняются по инструкциям. Поиск последних настроек и обход родительских стадий упрощены и могут повторно просматривать инструкции, поэтому в худшем случае общая сложность не линейная. Для обычных Dockerfile из десятков или сотен строк этого достаточно; для больших корпусов можно добавить заранее вычисляемое состояние стадий и кеширование .dockerignore.
