# Dockercheck · проверка безопасности Dockerfile

Небольшой статический анализатор Dockerfile на Python. Находит распространённые ошибки безопасности и качества, объясняет проблему и возвращает код завершения для CI. Учебный проект по теме «Лучшие практики безопасности для Dockerfile».

**26 правил · 18 примеров Dockerfile · текст / JSON / SARIF · Python 3.11+ · без зависимостей при запуске.**

Проект не собирает и не запускает проверяемый Dockerfile, не отправляет его в сеть и не требует установленного Docker. Это проверка исходного файла, а не сканер CVE и не сертификат соответствия CIS.

## Быстрый старт

Из папки проекта:

```bash
python -m dockercheck examples/bad/root/Dockerfile
```

На Windows можно использовать `py -3` вместо `python`. Устанавливать пакеты не нужно.

Пример части результата:

```text
examples/bad/root/Dockerfile · стадий: 1
  6: ERROR   DF006 [стадия 0] — Финальный образ явно запускается от root
      → Создайте пользователя и переключитесь на него перед CMD/ENTRYPOINT.
```

Для этого файла программа завершится с кодом `1`: найденные ошибки — ожидаемый результат демонстрации.

Проверка корректных примеров:

```bash
python -m dockercheck examples/good --fail-on warning
```

Будут показаны необязательные рекомендации, например закрепить digest образа. Ошибок и предупреждений в этих примерах нет, код завершения — `0`. Каталог сканируется рекурсивно: `Dockerfile`, `Dockerfile.*`, `*.Dockerfile`. Каталоги `.git`, `.venv`, `.tools`, `node_modules` и файлы `*.bak` пропускаются.

При желании можно установить команду в своё виртуальное окружение:

```bash
python -m pip install -e .
dockercheck --help
```

Это необязательный вариант; для установки нужен setuptools, который pip при необходимости загрузит отдельно.

## Что проверяется

- Базовые образы: отсутствующий тег, `latest`, digest, переменные в `FROM`.
- Финальный пользователь: явный root и отсутствие явно заданного `USER`.
- Секреты в `ARG`/`ENV`, копирование `.env`, `.ssh` и некоторых приватных ключей.
- Загрузка скрипта прямо в shell, отключение TLS-проверки, удалённый `ADD`.
- Использование apt, apk, pip и npm, очистка кешей в том же слое.
- JSON-форма запуска, абсолютный `WORKDIR`, `chmod 777`, `sudo`.
- Широкий `COPY` без `.dockerignore`, устаревшие инструкции, `ONBUILD`.
- Необязательные требования к здоровью контейнера и стилю Dockerfile.

Каждое правило имеет постоянный ID, уровень и рекомендацию. Полный [стандарт и чек-лист](docs/checklist.md) объясняет причины и исключения.

### Уровни и коды завершения

| Уровень | Что означает |
| --- | --- |
| `error` | Риск, который стандарт требует устранить или обоснованно исключить |
| `warning` | Проблема или решение, требующее проверки человеком |
| `info` | Рекомендация, не блокирующая CI по умолчанию |

По умолчанию сборку блокируют ошибки и предупреждения. Настройка порога:

```bash
python -m dockercheck Dockerfile --fail-on error
python -m dockercheck examples --fail-on none
```

`0` — порог не превышен; `1` — найдены нарушения порога или ошибка синтаксиса; `2` — ошибка аргументов, чтения, записи или конфигурации. `--fail-on none` не скрывает синтаксическую ошибку: непроверенный файл не считается успешным.

## Отчёты и CI

```bash
python -m dockercheck Dockerfile --format json --output reports/result.json
python -m dockercheck Dockerfile --format sarif --output reports/result.sarif
python -m dockercheck Dockerfile examples/good --context .
```

`--context` задаёт настоящий корень Docker build context для проверки `.dockerignore`. По умолчанию это папка каждого Dockerfile. Наличие непустого файла проверяется, правильность всех его шаблонов не доказывается. Dockerfile-специфичные ignore-файлы пока не поддерживаются.

SARIF содержит ID правил и строки исходного файла; JSON — также сводку и количество подавленных находок. Значения аргументов Dockerfile в отчёты не включаются. В GitHub Actions настроены тесты на Windows/Ubuntu и сохранение SARIF как артефакта. Отдельная [инструкция CI](docs/ci.md) объясняет подключение и пороги.

## Исключения

Глобально:

```bash
python -m dockercheck Dockerfile --ignore DF003,DF022
```

Локально, отдельным комментарием **перед нужной инструкцией**:

```dockerfile
# dockercheck: ignore=DF022 reason=Health probes configured in Kubernetes deployment
FROM alpine:3.21
USER 10001
CMD ["true"]
```

Причина обязательна. Неизвестный ID — ошибка конфигурации. Исключение действует на следующую инструкцию, а не на весь файл. Требования к отсутствующему `USER`/`HEALTHCHECK` привязаны к `FROM` финальной стадии; явный root — к действующему `USER`, включая унаследованный. Количество реально подавленных находок видно в отчёте.

## Автоисправление

```bash
python -m dockercheck examples/bad/legacy/Dockerfile --dry-run
python -m dockercheck path/to/Dockerfile --fix
```

Сейчас автоматически исправляется только **регистр ключевых слов** (`DF025`): `from` → `FROM`, `run` → `RUN`. Аргументы, shell-код и содержимое heredoc не меняются. Предварительный diff скрывает аргументы, чтобы не вывести секреты в CI.

Перед изменением создаётся точная копия `Dockerfile.bak`. Если она уже существует, программа отказывается перезаписывать её. Сохраняются BOM и окончания строк; запись выполняется через временный файл и замену. Символические ссылки не исправляются. После изменения файл проверяется заново: оставшиеся проблемы всё ещё могут дать код `1`.

Программа не выбирает за разработчика версию образа, не создаёт пользователя с неизвестными правами и не переводит shell-команду в JSON автоматически. Такие изменения могут сломать приложение; для них выводится рекомендация.

## Тестирование

```bash
python -m unittest discover -s tests -v
python scripts/evaluate.py
```

Тесты проверяют все 26 правил, наследование стадий, переносы строк, JSON-форму, heredoc, исключения, пороги CI, отчёты, автоисправление и регрессии ложных срабатываний. Временные файлы создаются в `.test-tmp` и удаляются после тестов.

`examples/manifest.json` — ручная разметка ожидаемых правил для 18 файлов. Скрипт оценки сравнивает пары «файл — правило» и печатает TP/FP/FN, precision и recall. Это внутренний демонстрационный корпус, а не независимая оценка качества на реальных проектах. Подробности и ограничения — в [отчёте о проверке](docs/validation.md).

## Запуск в Docker

```bash
docker build -t dockercheck-local .
```

Из PowerShell, в папке с проверяемым Dockerfile:

```powershell
docker run --rm --mount "type=bind,source=$((Get-Location).Path),target=/work,readonly" dockercheck-local /work/Dockerfile
```

Из Bash:

```bash
docker run --rm --mount "type=bind,source=$(pwd),target=/work,readonly" dockercheck-local /work/Dockerfile
```

Контейнер работает под UID/GID `10001`. Для проверки достаточно read-only mount; `--fix` требует доступного для записи каталога. Для файла отчёта также нужен отдельный writable mount. Docker-образ предназначен для CLI: постоянно работающий сервис и `HEALTHCHECK` ему не нужны.

## Что инструмент не может доказать

Проверка статическая и эвристическая. Она не узнаёт пользователя, `ONBUILD`-триггеры и пакеты произвольного внешнего базового образа, не обращается к registry и не ищет CVE. Поэтому отсутствие `USER` — предупреждение, а не утверждение о запуске от root. Наследование поддерживается между стадиями текущего файла.

Shell-анализ рассчитан на типовые команды. Сложные Bash-конструкции, функции, переменные, альтернативные package manager wrappers и содержимое скачанных скриптов требуют ручной проверки. Наличие строки очистки или настройки кеша не доказывает, что ветка выполнится. Нельзя измерить размер итогового образа по одному Dockerfile.

Парсер поддерживает распространённый Linux Dockerfile, `# escape`, переносы, JSON-форму и простые heredoc. Это не полная замена парсеру BuildKit: Windows PowerShell, произвольные heredoc-конструкции, нестандартные frontend-инструкции и расширенные подстановки ARG могут потребовать доработки. При разборе неподдерживаемой инструкции файл получает `PARSE`, остальные файлы продолжают проверяться.

Для реального CI следует сочетать проверку с `docker build --check`, сборкой, сканированием зависимостей/образа и тестовым запуском. Разграничение namespaces, cgroups, capabilities, seccomp и доступ к Docker daemon относятся к среде запуска и не проверяются здесь. Обзор — в [основах Docker](docs/docker-basics.md).

## Материалы для сдачи

```bash
python scripts/package.py
```

В `dist/dockerfile-security-checker.zip` попадут исходники, схема, тестовые Dockerfile, тесты и документация. Git, кеши, резервные копии и временные отчёты исключаются. Рядом создаётся SHA256 архива. ZIP можно загрузить в Облако Mail и открыть доступ по ссылке; сам скрипт ничего не публикует.

Схема доступна в [SVG](docs/algorithm.svg) и [Mermaid](docs/algorithm.mmd). Рекомендации опираются на [официальную документацию Docker](https://docs.docker.com/build/building/best-practices/), [Dockerfile reference](https://docs.docker.com/reference/dockerfile/) и общую направленность [CIS Docker Benchmark](https://www.cisecurity.org/benchmark/docker). Версии, ограничения и подробные ссылки перечислены в [источниках](docs/sources.md).

В учебном задании указано требование к коду, написанному без генерации ИИ. Этот проект подготовлен с помощью ИИ; перед сдачей следует согласовать такой формат с преподавателем и самостоятельно разобраться в реализации.
